## D-1 · 行内铅笔按钮必须保留（2026-11-14 用户拍板）

**决策：保留用户消息动作行里的铅笔按钮，不删。**

用户原话：

> 「那个有用吗？为什么要删掉？面板那个玩意大多数人都懒得用的，这个放在消息框
> 下面的这样一个铅笔是非常好用的」

### 为什么不能删

1. **使用成本不同**：铅笔是**就地**操作 —— 看到想改的消息，点一下就在原地改。
   面板要「打开面板 → 在列表里找到那条 → 选中 → 点回滚 → 再回输入框改」，
   步骤多 4 倍。能用 ≠ 好用。
2. **面板的定位不是替代铅笔**：面板面向**批量 / 任意消息 / 会话级操作**
   （遮蔽单条、删整条会话、跨页选历史消息、恢复区）。这些铅笔确实做不到，
   但这**不构成删铅笔的理由** —— 两者是不同场景，不是子集关系。
3. **用户明确说过懒得用面板**。把高频操作赶到低频入口，是负优化。

### 历史教训（重要）

铅笔在 0.19.0 曾被「动作区收敛」审计删掉，0.20.0 又被用户要求加回来。
**同一个功能删了又加 = 浪费两轮迭代。** 后续审计不要重复这个错误。

### 如果将来要动它

必须先回答这三个问题，并在本文件留下新记录：
1. 用户是否明确说「不要铅笔了」？
2. 有没有**同等成本**的替代（不是"面板也能做"）？
3. 删掉后「就地改一条消息」要几步？

## D-2 · 面板（OpsPanel）保留

面板承担铅笔做不到的能力：批量遮蔽、删整条会话、跨页选历史消息、
恢复区（dock）、搜索。**不删。**

## D-3 · 回撤必须诚实告知「不是删除」

DSH 是 append-only，回撤只 append `surfaceOp: replace` marker，**原文仍在
本地会话文件里**（实测 161 条被回撤消息原文可读）。opencode 是真删/字段遮蔽，
用户预期完全不同。

因此任何回撤入口都必须让用户知道「AI 看不到，但原文还在文件里、可恢复」。
文案可以精简（0.24.0 已从 130 字压到 74 字），但**告知不能删**。

## D-4 · 引用让位宿主，不自己造按钮（2026-11-13 拍板）

宿主 `dsh-message-quotes` 已有完整划词引用（选中多少引多少）。我们旧按钮
选区体系不匹配，会退化成塞 600 字全文进 prompt；而 `deriveMessages()` 本就
给出完整历史，引用未遮蔽消息 = 同一内容进 prompt 两遍。

**不恢复自定义引用按钮。**

## D-5 · 分叉让位官方（2026-11-13 拍板）

官方 `TurnTailNodeView` 的 `MessageIconActions` 本就有 `sessions.fork`
分支按钮。0.12 起我们把它藏了（`suppressHostBranch`）又自己造行内 fork，
是重复造轮子。**已删抑制 + 删行内 fork，恢复官方按钮。不恢复行内 fork。**

## D-6 · 铅笔可用性验证方法（避免再次误判）

2026-11-14 实测，可见性结论如下（真实 Chromium，会话
`session-62374e92-e411-4190-9692-22da9a3abd0b`）：

```
9 个 user row，其中 6 个 hidden="until-found"（历史折叠，height 0）、3 个可见
3 个可见 row 全部 edit:true / revert:true
铅笔计算样式：opacity:1, visibility:visible, display:flex, 28x28
```

### ⚠️ 探针陷阱（曾导致误判"铅笔坏了"）

1. **`document.querySelector('.mopsUserEdit')` 会命中折叠行里的按钮**
   → `getBoundingClientRect()` 返回 `height:0` → 误判"按钮不可见"。
   正确做法：先 `filter(x => x.getBoundingClientRect().height > 0)` 筛可见 row，
   再从**可见 row 内部**取按钮。
2. **Playwright 的 `.first()` 同样命中折叠行** → `click()` 报
   "element is not visible"。必须用页面内 `evaluate` 精确选可见行的按钮。
3. **会话加载有延迟**：不等待就查会得到 `total:0`（插件还没注入）。
   必须等 `[data-chat-flow-kind="user"]` 出现 + 额外 settle。

**结论：铅笔从未损坏。之前所有"点不到"的报错都是探针选择器问题。**
